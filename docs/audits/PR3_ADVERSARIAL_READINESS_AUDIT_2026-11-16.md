## 3. Priority findings — precise implementation anchors

| ID | Sev. / grade | Observation and required regression |
| --- | --- | --- |
| LND3-P0-01 | **P0 SOURCE-CONFIRMED** | `src/api/server.ts:287-289,484-526`: `GET /claims`, `/dispatch/capacity-reconciliation`, `/finance/reconciliation`, `/dispatch/pickup-queue`, `/partner/expected-receipts`, `/finance/fiscal-receipts`, and `/orders` rely on authentication/organization only, with **no role-, partner- or customer-specific query filters**. A logged-in user in the same organization can receive sensitive rows for other users/roles. `GET /orders/:id` also returns the full order object through `loadOrder`; partner/courier field-level projection is absent. Test forbidden role, foreign customer, foreign partner and minimal fields for every endpoint. |
| LND3-P0-02 | **P0 SOURCE-CONFIRMED** | `src/services/partner.ts` `receiveHandoff` assigns an unassigned order to the **requesting partner**; `startInspection`, `proposeAdjustment`, `startProcessing`, `recordQualityCheck` query by organization/order but do not require explicit `order.assignedPartnerId === principal.partnerId`. `disputePartnerLine` in `src/services/finance.ts` does not require ownership of the invoice's partner for `partner_finance`. Tests: partner B may not claim A/unassigned orders, change A's price/QC or dispute A's bill. |
| LND3-P0-03 | **P0 SOURCE-CONFIRMED** | `src/core/idempotency.ts` `withIdempotency` checks org/scope/key/hash on replay **without comparing persisted `actorId` or reauthorizing resource access**. Several command hashes omit actor/customer (`createCustomerInvoice`, `refundPayment`, `scheduleOrder`, `openClaim`). Replay with a known key can return cached resource data or bypass today's permission rules. Bind key ownership/authorization and scope to actor and target; test cross-principal replay and revoked membership. |
| LND3-P0-04 | **P0 HYPOTHESIS — high confidence from code** | `src/services/finance.ts` `refundPayment` reads `sum(refunds)` then inserts without a payment-intent row lock/atomic refundable-balance guard. Concurrent different keys can both pass their independent snapshot check. `capturePayment` permits independent full-value fake captures for the same order using different keys. Validate with two separate DB connections/barrier-controlled overlap; ensure no over-refund, duplicate capture or duplicated journal and bounded totals under retry. |
| LND3-P0-05 | **P0 SOURCE-CONFIRMED** | `src/services/orders.ts` `scheduleOrder` permits **both reservation IDs absent**; it does not prove supplied held reservation belongs to the order's customer, accepted quote, building or correct pickup/delivery kind. It may mark an order `scheduled` with zero or unrelated capacity. Enforce both required logical reservations or an explicitly documented deferred booking state, binding and atomic confirmation; test cross-customer same-tenant reservation hijack, wrong kind/building, expired hold and payment failure. |
| LND3-P0-06 | **P0 SOURCE-CONFIRMED** | `src/services/claims.ts` `openClaim` takes `garmentIds` without verifying membership of the target order, and optional `evidenceIds` are checked by organization **but not owner/order/purpose**. A user can associate a different order's asset with a claim and place a legal hold on it. Test per-object ownership, authorized evidence relations, access audit and legal-hold correctness. |
| LND3-P0-07 | **P0 GAP / SOURCE-CONFIRMED** | `POST /webhooks/payments/:provider` in `src/api/server.ts:458-465` is session-authenticated (no `public` setting), while `handlePaymentWebhook` does not check provider signature or trusted org mapping and merely inserts a row; a real external provider cannot use this endpoint, while an authenticated session can submit arbitrary event data. Replace with an independently authenticated provider adapter, signature verification, durable inbox processor and reconciliation. Keep fake provider fenced from real money. |
| LND3-P1-01 | **P1 SOURCE-CONFIRMED** | `src/services/delivery.ts`: `deliveredIds.length === allGarments.length` checks **length**, not exact set equality. Duplicate valid IDs can mark an order fully delivered while a different garment remains. For an Economy bag (zero garments) the `delivered` path never advances, and the partial path completes its stop without creating a next recovery stop. Test unique exact-set, bag-level proof, outstanding items and reattempt/reschedule. |
| LND3-P1-02 | **P1 SOURCE-CONFIRMED** | `src/services/partner.ts`: `recordQualityCheck` validates that supplied IDs are from the order but **not that the set covers all accepted items** before `ready`. Price adjustment acceptance moves the lifecycle to `processing` without clearly generating the treatment batch, reflecting revised invoice/approval lifecycle, or version-bounded consent for the proposed delta. A declined adjustment returns to `inspection` without implemented customer return handling. Add protected/mixed/item reconciliation tests. |
