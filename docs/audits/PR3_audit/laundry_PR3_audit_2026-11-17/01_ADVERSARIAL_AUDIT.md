### LAU-R2-006 | P0 | Evidence object authorization is incomplete (SOURCE-CONFIRMED, exploit needs integration repro)
Evidence: `src/services/workspace.ts:115-123` checks target existence and ownership **only when `ownerType === 'order'`**. For `ownerType === 'claim'` and `'custody_event'`, an authenticated customer/operator can register arbitrary owner UUIDs without checking claim/incident ownership. `listEvidence` at `:139-169` also restricts only `ownerType='order'`; for other owner types it returns same-organization evidence metadata, including `objectKey`, without verifying the caller's access to the owning claim/event. **Fix:** Introduce one permission function `authorizeEvidenceOwner(actor,ownerType,ownerId,purpose,action)` used by register/list/upload/preview/delete/export and legal-hold operations; verify tenant + customer/partner assignment + case scope; return safe 404; never return storage keys in public DTO; use short-lived server-authorized URLs. Add negative tests for customer A/B same tenant, partner A/B, claim ID, custody event ID, revoked access and audit trail.

### LAU-R2-008 | P1 | Route optimization yields fabricated geography if invoked (CONFIRMED algorithmic input bug)

### LAU-R2-009 | P1 | Cookie origin defense covers POST, not DELETE (CONFIRMED gap; attack exploitability not verified)

### LAU-R2-010 | P1 | Notification 'delivery' is not actual SMS/push/mail (CONFIRMED gap)
Evidence: `src/services/outbox.ts:40-97` converts domain events into *database* `notifications` rows, sets outbox state processed. No provider adapter delivery/acknowledgement is shown; ":push" is a label, not a delivered push. The processor claims rows with `FOR UPDATE SKIP LOCKED`, but the selection ignores `available_at <= now`; failed rows are immediately requeued by `requeueFailedOutboxEvents`, with no exponential backoff or DLQ delivery adapter. **Fix:** Separate domain outbox processing, notification scheduling, provider send/delivery receipt, attempts, backoff and dead letter. Provide fake sink and deterministic fault-injection tests; require live provider later with explicit approval.

### LAU-R2-011 | P1 | Payment inbox uses single transaction with per-row caught exceptions; failure atomics unclear (SOURCE-CONFIRMED risk)
Evidence: `src/services/payment-inbox.ts:25-65` processes multiple claimed events inside one DB transaction, catches each `applyEvent` error, sets event `failed` and continues; **a previously successful mutation inside that transaction is not automatically undone when caught**, unless all operations are structured to be atomic/idempotent. In particular an event that mutates state and then fails on posting could retain the state change while being marked failed. No per-event rollback/savepoint was established by inspection. Webhook adapter only supports `fake` provider and does not prove real signature/settlement schemes.
**Fix:** Apply each inbox event in an isolated transaction or savepoint, add idempotent source postings; model partial failures between state/ledger/event updates, amount and customer reference mismatches, concurrent events, repeated webhooks, chargeback vs refund. Collect fixtures of correct and corrupted provider events.

## Threat-model observations for the next red team

- **Object-level attacks:** same-tenant customers A/B, partners A/B, courier reassigned after offline sync, cross-claim media refs, reused seals, duplicate bag/garment identifiers, revoked sessions, same key under a different principal. Focus on root and every transition endpoint, not only the obvious GET list.
- **Financial races:** multiple capture keys; refund vs chargeback; receipt creation vs cancellation; adjustment approval after quote expiry; duplicated webhook with changed payload; fault between payment-intent transition and journal.
- **Custody:** no proof from QR alone; prevent double-confirm by a single actor; associate physical bag, seal, weight and item hash with two independently acknowledged parties; returned-unprocessed and partial delivery must create physical recovery tasks.
- **Operations:** shift late/abandoned, courier offline during transfer, partner rejects or is unavailable, route optimization unavailable, customer unreachable, mismatch between estimated and actual weight, wrong recipient, QC rewash; verify alerts to dispatcher and customer.
- **Data:** evidence when claim on hold, deletion requests, images of third parties, retention scheduler, export/download logged, no leaked object key or street-door codes to partner/finance.
